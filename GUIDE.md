# Введение

## Что это за база

**vrack2-journal-db** — база данных для временных рядов (метрик), написанная на
TypeScript. Она живёт в том же процессе, что и ваш код Node.js: отдельный сервер,
PostgreSQL и нативные зависимости не нужны. Данные хранятся на диске, а не в
памяти, и переживают перезапуск приложения.

Вот что она умеет:

- **Надёжная запись.** Строки сначала фиксируются на диске (WAL), сегмент
  записывается атомарно — краш не оставляет «половину файла» и не теряет данные.
- **Компактное хранение.** Данные лежат по колонкам со сжатием (дельты, словарь,
  RLE, числовые кодексы, gzip/zstd) — файл заметно меньше, чем тот же JSON.
- **Быстрый разбор по времени.** Запрос на период не читает файлы, целиком вне
  этого периода, — их границы лежат в маленьком файле `.meta` рядом.
- **Агрегация и запросы.** min/max/sum/avg/count, таймлайны, квантили, векторный
  скан (select/where/groupBy) и небольшой SQL.
- **Retention с предсказуемым размером.** Свежие данные — в высоком разрешении,
  старые — сгущаются и удаляются по TTL.

## Какие задачи она решает

Попробуйте собрать график потребления памяти вашего приложения — и станет
понятно, сколько мелочей тут ломается.

Допустим, вы пишете каждое значение в массив:

- память растёт вместе с числом записей — и не восстанавливается;
- данные нелинейны по времени: чтобы вытащить «последний час», приходится пройти
  по всему массиву;
- график из 200 000 точек на экране превращается в кашу, а из 50 — пропущены
  провалы. Нужно как-то «сгладить», но тогда теряются пики;
- после перезапуска приложения всё это исчезает — а хотелось бы видеть историю.

vrack2-journal-db закрывает каждый из этих пунктов:

- данные на диске и переживают перезапуск;
- запись только добавляет новые файлы — старые не трогаются, поэтому не нужно
  переписывать всё целиком;
- свежее держится в высоком разрешении, старое сгущается в более крупные бакеты —
  на графике всегда ровно столько точек, сколько нужно;
- запрос на период читает только нужные файлы, а не всё подряд.

Затем к этим проблемам добавляются агрегация, поиск по меткам, сжатие и очистка
старого — и всё это уже встроено.

## Где её применяют

- графики загрузки CPU / диска / сети / памяти;
- диагностика задержек HTTP / API / WebSocket;
- счётчики успешных/неудачных операций по времени;
- хранение телеметрии устройств (мультиметры, БП, датчики);
- «бесконечный» график, который не сдвигается по времени;
- кэш метрик для быстрого отображения и разбора.

Коротко: если вам нужно хранить данные «когда-то → значение» и потом смотреть их
по времени — это подходящий инструмент.

# Гайд

## Установка

```bash
npm install vrack2-journal-db
```

Два уровня:

- **Store** — каталог таблиц, привязанный к каталогу на диске.
- **Table** — таблица: `append` / `query` / `aggregate` / `scan` / `sql` / `compact` / `purge`.

Таблицу создаёте через `store.create(def)`. Описание `def` собирает `defineLogTable()`,
`defineUpsertTable()`, `defineSummingTable()` или `defineCollapsingTable()` — разница
только в движке (что делать со строками при `compact()`).

## Первый запуск

```ts
import { Store, defineLogTable } from 'vrack2-journal-db';

const store = new Store('./data');   // ./data — каталог на диске

// Таблица: строки вида { ts, host, value }
const cpu = store.create(defineLogTable({
  name: 'cpu',
  columns: { ts: 'delta', host: 'dictionary', value: 'auto' },
}));

cpu.append({ ts: Date.now(), host: 'web-1', value: 42.3 });

cpu.query('now-30d', 'now');  // строки за последние 30 дней
cpu.tail(10);                 // последние 10
cpu.stats();                  // сколько строк, байт, диапазон ts
cpu.compact();                // слить закрытые сегменты в один
cpu.close();
```

Можно держать несколько независимых `Store` в разных каталогах. Уже существующую
таблицу открывают по имени:

```ts
const cpu2 = store.open('cpu');
```

## Время

Везде, где нужно время — запись, запросы, агрегации, retention — принимается число
(миллисекунды) или строка.

- **Момент** — число или строка: `1700000000000`, `now-1d`, `now+1h`, `now-1h-1m`.
- **Интервал** (длительность) — `15s`, `10m`, `1h`, `1d`, `2w`, `3mon`, `1y`.
  Используется как размер бакета в `timeline` и разрешение тиры в `retention`.
- **Период** — это всегда **два аргумента** (`start`, `end`), каждый — число или строка:

```ts
cpu.query(1700000000000, 1700003600000);   // два числа (мс)
cpu.query('now-7d', 'now');                 // две строки
cpu.query(1700000000000, 'now');            // смешанно
```

Доступные единицы в строках:

| Суффикс | Значение |
|---|---|
| `ms` | миллисекунда |
| `s` | секунда |
| `m` | минута |
| `h` | час |
| `d` | день |
| `w` | неделя |
| `mon` | месяц — фиксированные 30 дней |
| `y` | год — фиксированные 365 дней |

## Таблицы

Таблица — именованный набор строк. Каждая строка — объект: `{ ts, ...поля }`, где
`ts` — время (миллисекунды), а остальные поля — данные.

### Создание таблицы

```ts
const cpu = store.create(defineLogTable({
  name: 'cpu',
  desc: 'Метрики CPU по хостам',
  columns: { ts: 'delta', host: 'dictionary', value: 'auto' },
}));
```

Параметры:

- **name** `cpu` — имя таблицы. Оно же — имя каталога на диске. Должно быть
  уникальным и не содержать `/`.
- **desc** — человек-читаемое назначение. Попадает в манифест `_store.json` и
  видно в `store.describe()`.
- **columns** — схема: поле → тип колонки.

Описание валидируется сразу в `define*Table()` — ошибки видны в месте объявления,
а не при первом `compact()`.

### Колонки

Тип колонки говорит, как это поле будет храниться на диске:

| Тип | Для чего |
|---|---|
| `raw` | как есть (JSON), без обработки |
| `dictionary` | строки с малым числом разных значений (`host`, `level`) — словарь |
| `delta` | числа, меняющиеся нескладно — хранятся дельты (`ts`) |
| `rle` | числа, стоящие «ступеньками» (повторы) |
| `auto` | библиотека сама выбирает по данным |
| `catchall` | «корзина» для полей вне схемы — JSON |

Поле `ts` обычно задают `delta`: временные метки — это монотонно растущие числа,
и хранить разницы между ними гораздо выгоднее, чем сами значения. Строки-метки —
`dictionary`: вместо повторения строки `web-1` тысячи раз, словарь хранит её один
раз, а в данных — индексы.

## Запись данных

Запись идёт по одной строке:

```ts
cpu.append({ ts: Date.now(), host: 'web-1', value: 42.3 });
```

`ts` — это время строки (миллисекунды). Вы задаёте его сами. Строка без числового
`ts` сохраняется, но не попадает в запросы по времени, таймлайны и квантили.

Запись **не** пишет файл на каждую строку — это было бы медленно и роняло бы SSD.
Что происходит под капотом, разобрано ниже в разделе [Запись: шаг за шагом](#запись-шаг-за-шагом).

Полезные операции:

```ts
cpu.flush();      // дописать активный сегмент на диск (WAL срезается)
cpu.compact();    // слить закрытые сегменты в один (дедупликация)
cpu.purge('now-30d'); // удалить строки старше 30 дней
cpu.clear();      // очистить таблицу полностью
```

## Чтение данных

Везде, где нужно время, принимается число (мс) или строка вида `'now-1d'`, `'now'`:

```ts
cpu.query('now-6h', 'now');   // строки за последние 6 часов
cpu.query(0, Date.now());     // всё
cpu.tail(10);                 // последние 10 строк
cpu.allRows();                // все строки, старые → новые
```

Чтение по времени дешёвое: файлы, целиком вне периода, **не читаются** — решение
берётся из файла `.meta` рядом с сегментом. Подробнее — [Чтение и файл .meta](#чтение-и-файл-meta).

## Агрегация

Агрегации считаются по диапазону времени:

```ts
cpu.aggregate('now-1h', 'now', [
  { field: 'value', fn: 'avg' },
  { field: 'value', fn: 'min' },
  { field: 'value', fn: 'max' },
  { field: 'ts',    fn: 'count' },
]);
// → { value_avg: 42.3, value_min: 1.0, value_max: 99.9, ts_count: 7184 }
```

Доступные функции: `min`, `max`, `sum`, `avg`, `count`. Считаются только по
числовым значениям поля; `null` и не-числа пропускаются.

Таймлайн разбивает период на бакеты и считает строки в каждом:

```ts
cpu.timeline('15m', 'now-6h', 'now');
// → [ { start, end, count, hasData }, … ] — 24 бакета по 15 минут
```

Квантили (percentile) — точные p50 / p95 / p99 и т.д.:

```ts
cpu.percentile('now-1h', 'now', [0.5, 0.95, 0.99]);
// → { p50: 12.1, p95: 60.2, p99: 98.7 }
```

## Скан и SQL

`scan()` — векторный разбор: выбрать колонки, отфильтровать, сгруппировать,
отсортировать, ограничить. Читаются только запрошенные колонки.

```ts
cpu.scan({
  start: 'now-1h',
  end:   'now',
  where: [{ field: 'host', op: 'eq', value: 'web-1' }],
  groupBy: ['host'],
  agg:   { value: ['avg', 'max'], ts: ['count'] },
  order: 'desc',
  limit: 10,
});
```

Операторы `where`: `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `in`, `nin`, `isNull`,
`isNotNull`.

`sql()` — небольшой SQL, который компилируется в `scan()`. Поддерживается и
`INSERT INTO`:

```ts
cpu.sql("SELECT host, AVG(value) AS value_avg FROM cpu WHERE ts > now-1h GROUP BY host");
cpu.sql("INSERT INTO cpu (ts, host, value) VALUES (1700000000, 'web-1', 42)");
```

## Движки

У таблицы есть **движок** — правило, что делать со строками при `compact()`. Это
аналог движков ClickHouse:

| Движок | Что делает `compact()` |
|---|---|
| `log` | строки не меняются; дубли схлопываются |
| `upsert` | по ключу остаётся строка с максимальным `version` |
| `summing` | по ключу суммируются указанные числовые колонки |
| `collapsing` | по ключу гаснут пары +1/−1 в колонке `sign` |

Пример — «состояние», где по `(host, metric)` держится самая свежая версия:

```ts
import { defineUpsertTable } from 'vrack2-journal-db';

const state = store.create(defineUpsertTable({
  name: 'state',
  columns: { ts: 'auto', host: 'dictionary', metric: 'dictionary', value: 'auto' },
  key: ['host', 'metric'],
  version: 'ts',
}));

state.append({ ts: 1, host: 'web-1', metric: 'cpu', value: 42 });
state.append({ ts: 2, host: 'web-1', metric: 'cpu', value: 43 });
state.compact();   // по (host, metric) одна строка: value = 43 (макс. версия)
```

`summing` — суммирует:

```ts
const hits = store.create(defineSummingTable({
  name: 'hits',
  columns: { ts: 'auto', host: 'dictionary', count: 'auto' },
  key: ['host'],
  sum: ['count'],
}));
```

`collapsing` — гасит пары +1/−1 (создание/отмена):

```ts
const orders = store.create(defineCollapsingTable({
  name: 'orders',
  columns: { ts: 'auto', id: 'auto', sign: 'auto' },
  key: ['id'],
  sign: 'sign',
}));
```

## Retention и тиры

Без retention таблица живёт вечно и растёт. `retention` задаёт, сколько и с каким
разрешением хранить:

```ts
const cpu = store.create(defineLogTable({
  name: 'cpu',
  columns: { ts: 'delta', host: 'dictionary', value: 'auto' },
  retention: '5s:1d,15s:1w,1m:1mon',   // 5-сек на 1 день, 15-сек на 1 неделю, 1-мин на 1 месяц
  agg: { value: 'avg' },                // как сгущать: среднее по value
}));
```

Каждая пара `res:ttl` — это **тир**: разрешение `res` на период `ttl`. Свежие
данные лежат в тонком разрешении, а по мере старения автоматически сгущаются в
более грубые бакеты (rollup) и удаляются после TTL (purge). Это происходит само по
мере `append()`, с троттлингом, чтобы не дёргать диск на каждую строку.

Итоговый размер ограничен: `≤ Σ(TTL × разрешение)`.

```ts
cpu.rollup();   // вручную: перенести состарившееся в более грубый тир
cpu.stats();    // [ { tier, resMs, ttlMs, rows, bytes, minTs, maxTs }, … ]
```

## CLI

В пакете есть CLI `vrack2-journal`:

```bash
npm i -g vrack2-journal-db

vrack2-journal create  --data ./data --name cpu --columns ts=delta,host=dictionary,value=auto
vrack2-journal append  --data ./data --name cpu --ts 1700000000 --field host=web-1,value=42
vrack2-journal query   --data ./data --name cpu --from now-1d --limit 50
vrack2-journal stats   --data ./data
vrack2-journal compact --data ./data --name cpu
vrack2-journal tables  --data ./data
```

`--ts` — миллисекунды (числа меньше `1e12` трактуются как секунды); `--from/--to`
— число или `'now-1d'`. Движки кроме `log` — через `create --engine upsert --key
host --version ts` (аналогично `summing`/`collapsing`).

# Как это работает

## Слои

Сверху вниз:

```
Store      — каталог таблиц + общий кэш сегментов
 └─ Table  — одна таблица: 1 журнал (без retention) или N (тиры)
     └─ Journal — каталог на диске: N сегментов + WAL + блокировка
         └─ Segment — один файл с чанком строк (до 10 000)
             └─ Column — одна колонка со своей стратегией хранения
```

```
./data/
├─ _store.json          # манифест: описание всех таблиц
└─ journals/
   └─ cpu/
      ├─ seg_*.seg      # сегменты — сами данные (колонки + сжатие)
      ├─ seg_*.meta     # границы min/max ts + саммари (для быстрых чтений)
      ├─ wal.log        # буфер записи — страховка при крахе
      └─ .lock          # владелец журнала (PID процесса)
```

Ключевое свойство — **append-only**: данные только добавляются. Каждый новый блок
строк — новый файл-сегмент, старые файлы не переписываются. Из этого следуют
надёжная запись, параллельное чтение и простая очистка (сегмент целиком старше
срока удаляется одним `unlink`).

## Запись: шаг за шагом

Допустим, `rowsPerSegment = 10000` и `walBatchSize = 512` (значения по умолчанию).

```
1. cpu.append({ ts: 1, value: 42 })
   → строка кладётся в буфер в памяти (walBuf)
   → строка кладётся в активный сегмент (в памяти)

2. cpu.append({ ts: 2, value: 43 })
   → буфер: 2 строки, активный сегмент: 2 строки

   ...

512. cpu.append({ ... })
   → буфер набрал 512 строк (или 1 МБ) → запись в wal.log ОДНИМ системным вызовом
   → буфер очищен

   ...

10000. cpu.append({ ... })
   → активный сегмент набрал 10000 строк → flush():
       a) wal.log дописан на диск (целиком)
       b) сегмент записан во временный файл seg_XXX.seg.tmp
       c) seg_XXX.seg.tmp переименован в seg_XXX.seg  (атомарно)
       d) wal.log срезан — его строки уже в сегменте
   → создан новый активный сегмент
```

Обратите внимание: `append()` **не** пишет файл на каждую строку. Строка живёт в
буфере в памяти и уходит на диск **пачками**. Это и скорость, и надёжность: один
системный вызов на 512 строк вместо одного на строку.

## Почему краш не теряет данные

Рассмотрим каждый момент возможного краха:

```
До шага (b) — сегмент ещё не записан:
   Строки уже в wal.log (они ушли пачкой). При следующем открытии wal.log
   дочитывается, и строки возвращаются.

Между (b) и (c) — сегмент записан во временный файл, но не переименован:
   seg_XXX.seg.tmp — мусор, его можно удалить. seg_XXX.seg ещё нет (или старый).
   wal.log на месте. При следующем открытии — строки восстановятся из wal.log.

После (c) — сегмент на диске, wal.log срезан:
   Всё в seg_XXX.seg. Ничего не потеряно.
```

Единственный случай, когда данные теряются — `kill -9` или обрыв питания между
`append()` и сбросом буфера в `wal.log`. Перехватить это нельзя, это ограничение
любой WAL.

Переименование (rename) на одной файловой системе атомарно: наблюдатель видит либо
старый мир (файла ещё нет), либо новый (файл целиком). Полувыверенного файла на
диске не бывает.

## Сегмент и колонки

Сегмент — один файл с чанком строк. Внутри строки хранятся **по колонкам**, а не
по строкам. Зачем:

- **Меньше места.** Числа — дельтами, строки — словарём, повторы — RLE. В
  результате файл меньше, чем тот же объём в JSON.
- **Быстрее чтение.** Если запросу нужна только колонка `value`, не нужно
  разжимать колонки `host` и `ts`.

На выбор стратегии влияет тип колонки (`raw`/`dictionary`/`delta`/`rle`/`auto`/
`catchall`). `auto` — библиотека сама смотрит на данные и выбирает.

Форматы файлов:

- **v1** — чистый JSON (наследование от JS-версии)
- **v2** — gzip + CRC32 (по умолчанию)
- **v3** — бинарные блобы колонок (кодек + словарь + zstd/gzip + CRC32)

Старые версии читаются без миграции; миграция в v3 — ленивая, при `compact()`.

## Чтение и файл .meta

Рядом с каждым сегментом лежит маленький файл `.meta`:

```
{ "minTs": 1700000000000, "maxTs": 1700003600000,
  "rowCount": 10000, "tsCount": 10000,
  "summaries": { "value": { "min": 1.0, "max": 99.9, "sum": 42300.0, "count": 10000 } } }
```

При чтении по периоду `[start, end]` база для каждого сегмента смотрит `minTs` и
`maxTs` из `.meta`:

```
Сегмент A: minTs=100, maxTs=200   — период [300, 400] → A не читается
Сегмент B: minTs=350, maxTs=450   — период [300, 400] → B читается
Сегмент C: minTs=500, maxTs=600   — период [300, 400] → C не читается
```

Сегмент A и C не разжимаются вообще — решение о том, что они вне периода, берётся
из `.meta`. Сегмент B разжимается, и в нём читаются только запрошенные колонки.

Для агрегаций, где сегмент целиком лежит внутри периода, `sum`/`min`/`max`/
`count` берутся прямо из `.meta.summaries` — без чтения данных. Это fast-path.

## Почему append-only

Типичная «таблица» в СУБД — это файл, который постоянно переписывается: строки
обновляются, индексы перестраиваются, блокировки на чтение. Это нормально для
OLTP, но плохо для временных рядов, потому что:

- данные только добавляются — обновлений почти нет;
- объём велик — переписывать всё целиком медленно;
- чтение и запись должны работать параллельно.

Append-only решает все три:

- **Запись** — один новый файл, старые не трогаются. Нет переписывания.
- **Чтение** — каждый процесс читает свой кэш сегментов. Блокировка только на
  запись (`.lock`).
- **Очистка** — сегмент, целиком старше нужного срока, удаляется одним `unlink`.
  Нет перекодировки «половины» файла.

Цена — дубли на границах сегментов и рост числа файлов. Это компенсируется
`compact()` (слияние закрытых сегментов) и авто-компактом (по умолчанию включён,
порог 4 сегмента).

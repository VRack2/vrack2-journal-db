# vrack2-journal-db — колоночная база данных для событий и логов

Маленькая append-only база данных на Node.js. Данные лежат обычными файлами в
каталоге, сервера и зависимостей нет: можно копировать каталог на другую машину,
бэкапить его `tar`'ом, читать файлы напрямую. Это TypeScript-версия проекта —
самая полная: строгие типы плюс сжатие файлов, гибкая схема, компактизация и
защита от потери данных при крахе.

## Для чего это

vrack2-journal-db хорошо подходит для данных, которые **только добавляются**: логи приложения,
события пользователей (`login`, `click`, `error`), метрики, временные ряды.
Типичный сценарий — записывать события по мере их поступления и потом выбирать
их по времени: «покажи мне всё между 14:00 и 15:00».

Это **не** универсальная база данных. Здесь нельзя обновить или удалить отдельную
строку, нет транзакций и произвольных индексов — только запись в конец, чтение
всего или выборки по временному диапазону. Для таких задач это осознанный обмен:
простота и предсказуемое хранение вместо гибкости SQL.

## Какие проблемы решает

**Повторяющиеся данные раздувают файл.** В JSON-логе строка `{"ts":1700000001,"level":"info"}`
повторяется тысячи раз — вместе с ключами и общими словами. vrack2-journal-db хранит данные
колонками и кодирует каждую колонку под её характер: повторяющиеся строки — как
индексы в словаре, растущие таймстампы — как разницы между соседями, серии
одинаковых значений — как «значение × количество». На реальных логах это даёт
уменьшение файла в разы (результаты воспроизводятся тестами из каталога
`test/` в репозитории).

**«Покажи вчера» не должно читать весь файл.** Каждый сегмент на диске хранит свой
минимальный и максимальный timestamp. Запрос по диапазону сначала смотрит эти
границы — сегменты, которые точно вне диапазона, вообще не читаются с диска.

**Краш в момент записи не должен терять данные или ломать файл.** Строки
копятся в журнале предзаписи (WAL) и уходят на диск пачками; при выходе процесса
(включая `process.exit()`, SIGINT/SIGTERM, uncaught exception) незаписанный буфер
гарантированно сбрасывается на диск. Сам сегмент записывается атомарно: сначала во
временный файл, затем переименовывается. В любом из двух случаев — процесс убит
посреди `append()` или посреди flush'а — данные либо уже на диске, либо легко
восстанавливаются при следующем открытии (подробнее ниже).

**Два процесса не должны писать в один журнал одновременно.** Пока журнал открыт,
он «заперт» для других процессов; попытка открыть его вторым даёт явную ошибку с
PID владельца. Если владелец умер, блокировка забирается автоматически — база не
остаётся «зависшей».

**Мелкие файлы накапливаются.** При частых flush'ах на диске появляется много
небольших сегментов. `compact()` сливает их в один файл и при этом повторно
применяет дедупликацию уже на границах бывших файлов — строки, которые раньше не
могли «увидеть» друг друга через границу файла, теперь схлопываются.

**Схема данных меняется со временем.** В реальных логах поля появляются и
исчезают. vrack2-journal-db не падает: отсутствующее поле читается как `null`, лишние поля
можно собрать в специальную «корзину» (`catchall`), а старые сегменты остаются
читаемыми после расширения схемы.

## Как это устроено

Иерархия простая — четыре уровня:

```
Store (несколько журналов)
 └── Journal (журнал: именованный поток событий со схемой)
      └── Segment (сегмент: пачка строк, на диске — один файл)
           └── Column (колонка: одно поле, закодированное своей стратегией)
```

**Журнал** — это именованный набор событий со схемой. Схема задаёт для каждого
поля способ хранения: `{ ts: 'delta', level: 'dictionary' }`. Пока журнал открыт,
новые строки попадают в **активный сегмент**, который живёт в памяти. Когда он
набирает `rowsPerSegment` строк (по умолчанию 100) — или при `close()` — сегмент
закрывается и записывается на диск одним файлом; открывается новый активный.

**Сегмент** хранит строки не построчно, а по колонкам: все значения поля `ts` —
вместе, все `level` — вместе. Это и даёт возможность кодировать каждое поле под
свой характер данных. Сегмент также помнит свой временной диапазон (`minTs`,
`maxTs`) — это то, на чём работают быстрые запросы по времени.

**Колонка** применяет одну из стратегий хранения:

| Тип | Что делает | Когда использовать |
|---|---|---|
| `raw` | Хранит значения как есть | Произвольные данные: объекты, уникальные строки |
| `dictionary` | Строки заменяются номерами в общем словаре | Повторяющиеся строки: уровни логирования, имена событий |
| `delta` | Хранит первое значение и разницы между соседями (только неубывающие числа) | Timestamps, счётчики |
| `rle` | Схлопывает серии одинаковых значений в «значение × количество» | Длинные повторы одного значения |
| `auto` | Сам выбирает стратегию по первым 50 значениям | Когда характер данных заранее неизвестен |
| `catchall` | Хранит JSON-«корзину» для полей, которых нет в схеме | Гибкие схемы (см. ниже) |

Конкретно это выглядит так. Сто строк с уровнями `info`, `warn`, `error`, …:

```json
// raw — каждая строка целиком:
{ "data": ["info", "warn", "error", "info", ...] }

// dictionary — словарь один раз, дальше только номера:
{ "dictionary": ["info", "warn", "error"], "data": [0, 1, 2, 0, ...] }
```

Или сто последовательных таймстампов `1700000000 … 1700000099`:

```json
// raw — сто полных чисел:
{ "data": [1700000000, 1700000001, ..., 1700000099] }

// delta — одно число и девяносто девять единиц:
{ "baseValue": 1700000000, "deltas": [1, 1, 1, ...] }
```

`auto` работает так: пока записано меньше 50 значений, они просто накапливаются.
На 50-м значении колонка смотрит на сэмпл и решает: все значения одинаковые →
`rle`; это неубывающие числа → `delta`; уникальных значений меньше половины →
`dictionary`; иначе → `raw`. Решение записывается в файл, дальше данные идут уже
в выбранную стратегию. Важный нюанс: если сегмент закрылся раньше 50 строк,
колонка остаётся «нерешённой» — и после компактизации, когда данные из нескольких
файлов сливаются, решение принимается заново на объединённом сэмпле (см. ниже).

### Дедупликация одинаковых строк

Если строка **полностью** совпадает с предыдущей записанной (все поля схемы
равны; корзина `catchall` сравнивается по содержимому), она не записывается
физически — в сегменте хранится только ссылка «эта логическая строка = та же, что
физическая N». При чтении ссылки разворачиваются обратно, поэтому `allRows()` и
`query()` возвращают все строки, как будто дублей не было. В статистике это видно:
`totalRows` — логических строк, `totalPhysicalRows` — реально записанных.

### Чтение: что происходит при открытии и запросе

При `open()` журнал **не читает данные** — он только смотрит список файлов в своём
каталоге и создаёт пустой активный сегмент. Файлы читаются с диска лениво, при
первом обращении к конкретному сегменту (в `query`, `allRows`).

Помимо каждого `<имя>.json` лежит крошечный сайдкар `<имя>.json.meta` — JSON из
границ `minTs`/`maxTs` и счётчиков строк (несколько десятков байт). Он пишется
атомарно вместе с сегментом, поэтому при открытии журнал поднимает границы всех
сегментов за микросекунды: `stats()`, `getTimeRange()` и пропуск файлов в
`query()` работают **без единого разжатого файла**. Сегменты старых версий без
`.meta` читаются как раньше — границы достаются из данных при первом обращении.

Прочитанные сегменты держатся в памяти — это кэш на `maxCachedSegments` штук
(по умолчанию 32). Если нужно больше, самые давно не использовавшиеся вытесняются;
при следующем обращении они просто перечитаются с диска. Для типичного журнала
это значит: горячие данные читаются из памяти, холодные — один раз с диска.

Запрос по времени `query(startTs, endTs)` идёт так: для каждого сегмента сначала
сравниваются его границы `minTs`/`maxTs`; если диапазон запроса их не пересекает,
файл **вообще не читается**. Внутри подходящих сегментов строки фильтруются уже по
значению `ts`.

Если нужны только самые свежие записи — `tail(n)` обходит сегменты от новых к
старым и останавливается, как только соберёт n строк: для «последних 10» из
журнала в сто тысяч строк читаются один-два последних файла, а не все.

### Запись и надёжность: что происходит при крахе

Здесь три механизма работают вместе. Разберём по шагам, что делает каждая запись:

1. **Строка сначала уходит в WAL** — файл `wal.log` (журнал предзаписи, write-ahead
   log). Одна строка — одна JSON-строка в файле. Запись на диск идёт пачками
   (по умолчанию 512 строк или 1 МБ накоплено — один системный вызов вместо одного
   на строку), но буфер гарантированно сбрасывается при любом выходе процесса:
   `close()`, `process.exit()`, SIGINT/SIGTERM, uncaught exception. Значит: даже если
   процесс мгновенно умрёт после `append()` — строки уже на диске и не потеряны
   (исключение — только `kill -9`/сбой питания; это ограничение любой WAL).

2. **Сегмент записывается атомарно.** Когда сегмент заполняется, он сначала
   пишется во временный файл `<имя>.json.tmp`, и только когда запись полностью
   завершена — переименовывается в `<имя>.json`. Переименование на одной файловой
   системе атомарно: наблюдатель видит либо старый мир (файла ещё нет), либо новый
   (файл целиком). Полувыверенного файла не бывает. Сразу после этого `wal.log`
   удаляется — все его строки уже внутри сегмента.

3. **При следующем открытии** журнал проверяет: есть ли в каталоге `wal.log`?
    Если да — значит, предыдущий процесс умер до flush'а. Строки из него
    проигрываются в активный сегмент (в том числе с дедупликацией), файл удаляется.
    Дальше журнал работает как ни в чём не бывало: `allRows()` вернёт и старые,
    и «спасённые» строки.

**Блокировка.** По умолчанию (`lock: 'pid'`) при открытии журнал создаёт файл
`.lock` со своим PID — это маркер «журнал занят». Второй процесс, пытающийся
открыть тот же журнал, получает ошибку вида `Журнал заблокирован процессом 12345`.
Если владелец блокировки умер (процесса с таким PID больше нет), новый процесс
забирает блокировку себе — ручную «разблокировку» делать не нужно. При `close()`
блокировка снимается.

Опция `lock: 'off'` отключает и создание, и проверку `.lock`: библиотека больше
не участвует в координации владельцев, это становится ответственностью приложения.

```ts
const j = new Journal('./data', { lock: 'off' }); // или Store({ lock: 'off' })
// override для одного журнала: store.openJournal('x', schema, {}, { lock: 'pid' | 'off' })
```

Когда это нужно: типичный случай — база внутри **worker_threads**. Воркер
разделяет PID с основным процессом, поэтому если воркер умирает (крах,
`terminate()`), его `.lock` выглядит как блокировка живого процесса и журнал
«застревает» до перезапуска приложения. Если вы сами контролируете владельца
(один воркер-обработчик + IPC, свой supervisor), открывайте с `lock: 'off'` —
и не забудьте снять осиротевший `.lock`, если база уже «застряла»:

Семантика при нескольких открытых инстансах одного журнала: каждый видит данные
на момент своего `open()` плюс то, что записал сам; новые сегменты другого
инстанса становятся видны после `close()`/reopen. Данные на диске сходятся в
любом случае — просто «живой» обмен между открытыми инстансами не предусмотрен.

```ts
fs.rmSync(path.join(dataDir, 'journals', <имя>, '.lock'), { force: true });
```

**Целостность файлов.** Новые файлы сегментов имеют формат v2: магические байты
`JSDB`, версия, gzip-сжатый JSON и 4-байтовая контрольная сумма (CRC32) в конце.
При чтении сумма проверяется **до** разжатия — повреждённый файл (обрыв записи,
битые сектора) отклоняется с явной ошибкой «повреждён: контрольная сумма не
совпала», а не превращается в мусорные данные. Старые файлы v1 (чистый JSON, как у
JS-версии из `../new`) читаются без изменений — база backward-совместима.

### Компактизация

Со временем на диске накапливается много закрытых сегментов. `compact()` сливает их
все в один файл:

```ts
const r = journal.compact();
// { mergedSegments: 5, logicalRows: 480, physicalBefore: 471, physicalAfter: 3 }
```

При слиянии происходит две полезные вещи. Во-первых, дедупликация применяется
заново — теперь уже и на границах бывших файлов: если последний ряд сегмента A и
первый ряд сегмента B одинаковы, раньше они хранились дважды (каждый файл не знал
о соседнем), а после слияния — один раз. Во-вторых, «нерешённые» `auto`-колонки
получают объединённый сэмпл и могут наконец выбрать стратегию: например, два файла
по 30 строк с двумя уникальными значениями каждый по отдельности не достигали порога
в 50 значений, а вместе — достигли, и колонка перекодировалась в `dictionary`.

Слитый файл записывается атомарно (tmp + rename), и только после этого старые файлы
удаляются. Активный сегмент компактизация не трогает.

### Гибкая схема

Три ситуации, которые раньше были ошибками или потерей данных:

**Отсутствующее поле.** Схема говорит «есть поле `val`», а в строке его нет —
раньше это было исключением. Теперь поле просто заполняется `null`, запись
проходит. При чтении таких строк `val` будет `null`.

**Лишние поля.** В строке пришли поля, которых нет в схеме. Если в схеме объявлена
колонка-корзина — `{ payload: 'catchall' }` — лишние поля собираются в неё и
читаются обратно как JSON-объект (в примере ниже `user` и `code`). Дедупликация
сравнивает содержимое корзин, поэтому строки с одинаковыми основными полями, но
разными «лишними», не схлопываются. Если корзины нет — лишние поля молча отбрасываются.

```ts
const j = new Journal('./data');
j.open('logs', { ts: 'delta', level: 'dictionary', payload: 'catchall' });

j.append({ ts: 1, level: 'info', user: 'alice', code: 42 }); // user, code → payload
j.append({ ts: 2, level: 'warn' });                           // без лишних → payload = null

const rows = j.allRows();
rows[0].payload; // { user: 'alice', code: 42 }
```

**Эволюция схемы.** Журнал можно открыть с расширенной схемой — старые сегменты
остаются читаемыми, новых полей в их строках просто не будет (придут `null`):

```ts
// раньше схема была { ts, val }; добавили поле extra
const j = new Journal('./data');
j.open('events', { ts: 'delta', val: 'dictionary', extra: 'raw' });

j.allRows(); // старые строки: extra === null; новые — с заполненным extra
```

## Использование

Установка из npm:

```bash
npm install vrack2-journal-db
```

Нужен Node.js ≥ 18, зависимостей нет (всё на встроенных `node:fs`/`zlib`).
Пакет — чистый ESM-модуль; TypeScript-типы идут в комплекте (`lib/*.d.ts`).

CJS-проекты: на Node ≥ 23 (и ≥ 22.12) обычный `require('vrack2-journal-db')`
работает через require(ESM). На более старых версиях — только динамический
`import()`.

> Разработка из исходников этого репозитория требует Node.js ≥ 23.6
> (запускает TypeScript нативно, сборка не нужна). Для сборки `npm run build` —
> результат лежит в `lib/`.

### Базовый цикл

```ts
import { Journal } from 'vrack2-journal-db';

// rowsPerSegment — сколько строк в одном файле сегмента (по умолчанию 100)
const j = new Journal('./data', { rowsPerSegment: 100 });

// open(имя, схема, метаданные). Метаданные — любые ключи-значения,
// например owner/version; они сохраняются в каждом сегменте.
j.open('events', { ts: 'delta', level: 'dictionary' }, { owner: 'me' });

for (let i = 0; i < 12; i++) {
  j.append({ ts: Date.now() + i, level: ['info', 'warn', 'error'][i % 3] });
}

j.query(startTs, endTs);   // выборка по временному диапазону (границы включены)
j.allRows();               // все строки в порядке записи
j.tail(10);                // последние 10 строк; старые сегменты не читаются зря
j.page(10, 20);            // limit/offset по журналу (asc/desc); см. «Пагинация» ниже
j.getMarks();              // отсортированные timestamps — удобно для таймлайна
j.getTimeRange();          // [minTs, maxTs] по всем сегментам
j.stats();                 // { segmentCount, totalRows, totalPhysicalRows, dedupRatio, timeRange }

j.clear();                 // полная очистка журнала (память + файлы), блокировка остаётся
j.close();                 // flush активного сегмента на диск + снять блокировку
```

Данные переживают перезапуск процесса:

```ts
const j2 = new Journal('./data');
j2.open('events', { ts: 'delta', level: 'dictionary' });
console.log(j2.allRows().length); // 12 — всё на месте, включая строки из WAL
j2.close();
```

### Несколько журналов через Store

`Store` управляет несколькими журналами в одном каталоге и держит общий кэш сегментов:

```ts
import { Store } from 'vrack2-journal-db';

const store = new Store('./data', { maxCacheSize: 20, defaultRowsPerSegment: 100 });
store.init(); // создаёт каталог data/journals/, если его ещё нет

// Какие журналы есть в каталоге (это просто список подкаталогов):
store.listJournals();
// → ['events', 'metrics']

// Метаданные журнала, не открывая его. Берутся из первого сегмент-файла;
// возвращает null, если журнал пуст или такого имени нет:
store.getJournalMetadata('events');
// → { name: 'events', segmentCount: 3, owner: 'me' }
//   (name + сколько сегментов на диске, плюс метаданные журнала)

// Id сегментов — имена файлов без .json, в хронологическом порядке:
store.listSegments('events');
// → ['seg_1786892460503_0', 'seg_1786892460503_1', 'seg_1786892460503_2']

// Ленивая загрузка одного сегмента: сначала смотрит свой кэш,
// если нет — читает файл с диска и кладёт в кэш. null, если файла нет:
const seg = store.loadSegment('events', 'seg_1786892460503_2');
seg.rowCount;         // 100 — сколько строк в этом сегменте
seg.minTs;            // 1700000200 — самая ранняя строка сегмента
seg.maxTs;            // 1700000299 — самая поздняя
seg.get('level', 0);  // 'info' — значение поля level в 0-й строке

// Сводная статистика по каталогу:
store.stats();
// → { baseDir: './data', journalCount: 2, openJournalCount: 1,
//     totalSegments: 5, cacheSize: 3, cacheMaxSize: 20,
//     journals: ['events', 'metrics'] }

// Открыть журнал для записи/чтения (создаёт Journal внутри store):
const j = store.openJournal('events', { ts: 'delta', level: 'dictionary' }, { source: 'api' });
j.append({ ts: Date.now(), level: 'info' });

store.closeAll(); // закрыть все открытые журналы (flush + снять блокировки)
```

### Последние N записей журнала

Типичный сценарий «покажи последние события» — без чтения всего журнала.
`tail(n)` сам подтягивает данные с диска, если они ещё не в памяти: сегменты
обходятся от новых к старым, и как только собрано n строк, более старые файлы
вообще не читаются:

```ts
import { Journal } from 'vrack2-journal-db';

// Процесс только что стартует — ничего ещё не загружено, данные на диске.
const j = new Journal('./data');
j.open('events', { ts: 'delta', level: 'dictionary' });

const last10 = j.tail(10); // последние 10 строк в хронологическом порядке (старые → новые)
// → [ { ts: 1700009960, level: 'info' }, ..., { ts: 1700009995, level: 'warn' } ]

j.close();
```

То же самое через Store — `openJournal` возвращает обычный `Journal`:

```ts
const store = new Store('./data');
store.init();
const j = store.openJournal('events', { ts: 'delta', level: 'dictionary' });
const last10 = j.tail(10);
j.close(); // или store.closeAll()
```

### Пагинация: `page(limit, offset?, order?)`

Универсальный срез журнала в порядке записи — «LIMIT/OFFSET» поверх всех строк.
`tail(n)` — частный случай этого же обхода (последние n строк).

- `order='asc'` (по умолчанию) — старые → новые, `offset` считается от самых старых;
- `order='desc'` — свежие → старые, `offset` считается от самой свежей.

Сегменты, целиком лежащие до нужного окна, **не читаются с диска** — они
пропускаются по счётчикам строк из `.meta`. Чтобы прочитать окно в середине
журнала, достаточно открыть только один-два соседних файла.

```ts
j.page(10);                 // первые 10 строк (старые → новые)
j.page(10, 20);             // пропустить 20, взять следующие 10 — обычная пагинация
j.page(10, 0, 'desc');      // 10 самых свежих, свежие → старые
j.page(50, j.allRows().length - 50); // эквивалент tail(50), но в любом порядке обхода
```

### Компактизация и статистика после неё

```ts
const r = j.compact();
console.log(r.mergedSegments, r.physicalBefore, r.physicalAfter);
// 5 файлов слито; физических строк было 471, стало 3 — дедупликация на границах сработала

j.stats().dedupRatio; // отношение записанных строк к логическим
```

### Полная очистка журнала

`clear()` удаляет все записи из памяти и с диска — файлы сегментов, их сайдкар'ы
`.meta`, `wal.log` (включая строки в WAL-буфере) и `.tmp`-остатки прерванной
записи. Блокировка остаётся за владельцем, журнал не закрывается:

```ts
j.clear();                          // было 2M строк — теперь чистый журнал
j.append({ ts: Date.now(), msg: 'с нуля' }); // писать можно сразу
```

Это не «удаление по условию» (такого нет — база append-only), а полный сброс.
Если нужен TTL («выбросить старее N дней»), это отдельная фича на тех же
`.meta`-границах сегментов.

## Цифры (нагрузочный тест)

`test/test-load.ts` — долгий прогон: 2 000 000 «реалистичных» строк лога
(12 полей, catchall-корзины, ~40 сегментов по 50K строк). Запуск:

```sh
node --max-old-space-size=8192 test/test-load.ts   # LOAD_ROWS=500000 — быстрее
```

Результаты на MacBook (Apple Silicon), Node 25:

| Метрика | Значение |
| --- | --- |
| Скорость записи | **~530K строк/с** (2M за 3.8 с) |
| Пиковая память при записи | ~810 МБ RSS |
| Размер на диске (gzip v2) | **15.0 МБ** на 2M строк (~7.8 Б/строку) |
| То же без gzip (чистый JSON) | ~250 МБ → коэффициент сжатия **~16x** |
| `compact()`: 40 файлов → 1 | 15.0 → 14.6 МБ, дедупликация на границах |
| Холодное `open()` + `stats()` | ~1 мс (по сайдкар'ам `.meta`, без чтения сегментов) |
| `allRows()` по 2M строк | ~1.5 с |
| `query()`: 100K строк в диапазоне | ~77 мс; диапазон мимо данных — 0 мс (файлы не читаются) |

Полная целостность проверяется агрегатами по всем 2M строкам после холодного
reopen и после compact'а.

## Формат данных на диске

Каталог базы выглядит так:

```
data/
└── journals/
    └── events/
        ├── seg_1786892460503_0.json   # закрытый сегмент (v1 — JSON, v2 — gzip + CRC32)
        ├── seg_1786892460503_0.json.meta  # границы min/max ts и счётчики (~60 байт)
        ├── seg_1786892460503_1.json
        ├── wal.log                    # строки, записанные ещё до flush'а; удаляется после него
        └── .lock                      # блокировка владельца; живёт пока журнал открыт
```

Содержимое сегмента (v1 — так он выглядит как JSON; v2 — тот же JSON, но gzip-сжатый
и с контрольной суммой):

```json
{
  "id": "seg_1786892460503_0",
  "schema": { "ts": "delta", "level": "dictionary" },
  "metadata": { "owner": "me" },
  "rowCount": 100,
  "physicalRowCount": 85,
  "minTs": 1700000000,
  "maxTs": 1700000099,
  "columns": {
    "ts":     { "type": "delta", "baseValue": 1700000000, "deltas": [1, 1, ...] },
    "level":  { "type": "dictionary", "dictionary": ["info", "warn", "error"], "data": [0, 1, 2, ...] }
  },
  "dedupMap": [0, 0, 0, 1, 2, ...]
}
```

`rowCount` — сколько строк «видит» читатель; `physicalRowCount` — сколько реально
записано (разница — дедупликация); `dedupMap[i]` — к какой физической строке
относится i-я логическая. Метаданные в сегменте — снимок на момент его записи:
позднее `updateMetadata()` влияет только на журнал и будущие сегменты, уже
записанные файлы не переписываются (сегменты неизменяемы).

## Отличия от JS-версии (`../new`)

JS-версия — базовый функционал: журналы, колонки, дедупликация, запросы по времени,
файлы v1. TypeScript-версия содержит всё то же плюс: строгую типизацию (strict mode),
сжатие файлов с контрольной суммой (v2, старые файлы читает), гибкую схему
(null-падинг, catchall, эволюция схемы), компактизацию и надёжность (WAL, блокировки).

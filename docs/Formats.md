# Форматы хранения и кодеки

Повторяющиеся данные раздувают файл: в JSON-логе строка `{"ts":1700000001,"level":"info"}`
повторяется тысячи раз — вместе с ключами. vrack2-journal-db хранит данные
**колонками** и кодирует каждую колонку под её характер. Эта страница — как
данные лежат на диске: типы колонок, числовые кодексы, бинарный формат сегмента,
сжатие, структура каталога.

## Типы колонок

Каждое поле в схеме — колонка со своей стратегией хранения:

| Тип | Что делает | Когда использовать |
|---|---|---|
| `raw` | Хранит значения как есть | Произвольные данные: объекты, уникальные строки |
| `dictionary` | Строки заменяются номерами в общем словаре | Повторяющиеся строки: уровни логирования, имена событий |
| `delta` | Хранит первое значение и разницы между соседними (только неубывающие числа) | Timestamps, счётчики |
| `rle` | Схлопывает серии одинаковых значений в «значение × количество» | Длинные повторы одного значения |
| `auto` | Сам выбирает стратегию по сэмплу | Когда характер данных заранее неизвестен |
| `catchall` | Хранит JSON-«корзину» для полей, которых нет в схеме | Гибкие схемы (см. `Querying.md`) |

Конкретно это выглядит так. Сто строк с уровнями `info`, `warn`, `error`, …:

```json
// raw — каждая строка целиком:
{ "data": ["info", "warn", "error", "info", ...] }

// dictionary — словарь один раз, дальше только номера:
{ "dictionary": ["info", "warn", "error"], "data": [0, 1, 2, 0, ...] }
```

Или сто последовательных таймстампов `1700000000 … 1700000099`:

```json
// raw — сто полных чисел:
{ "data": [1700000000, 1700000001, ..., 1700000099] }

// delta — одно число и девяносто девять единиц:
{ "baseValue": 1700000000, "deltas": [1, 1, 1, ...] }
```

### Автовыбор (`auto`)

Пока записано меньше 50 значений, они просто накапливаются. На 50-м значении
колонка смотрит на сэмпл и решает: все значения одинаковые → `rle`; это неубывающие
числа → `delta`; уникальных значений меньше половины → `dictionary`; иначе → `raw`.
Решение записывается в файл, дальше данные идут уже в выбранную стратегию.

Важный нюанс: если сегмент закрылся раньше 50 строк, колонка остаётся
«нерешённой». После компактизации, когда данные из нескольких файлов сливаются,
решение принимается заново на объединённом сэмпле (см. `Maintenance.md`).

## Файловый формат сегмента (v4)

Единственный формат сегментов — бинарный контейнер **версии 4**: плотные
числовые кодексы вместо JSON, сжатие, CRC32. Сегмент всегда пишется файлом
`<имя>.seg`; других версий читатель не принимает (байт версии ≠ 4 — явная
ошибка `SFW3_BAD_VERSION`).

```
[0..3]     "JSDB"            магические байты
[4]        4                 версия контейнера (другая → SFW3_BAD_VERSION)
[5..7]     00 00 00          зарезервировано
[8..11]    headerLen (u32 LE)
[12 ..]    header JSON (UTF-8): схема, саммари, walSeq, кодек колонки,
           порядок колонок, способ сжатия, rowMapLen, clusterKey
для каждой колонки (в порядке columnOrder):
[blobLen u32]
[сжатый блоб]                gzip или zstd
[хвост rowMap]               rowMap как u32 LE на логическую строку
[N-4..N-1] CRC32 (u32 LE)    контрольная сумма всех предыдущих байтов
```

CRC проверяется **до** разжатия — повреждённый файл (обрыв записи, битые
сектора) отклоняется явно, а не превращается в мусорные данные. Файл версии 4
без `rowMapLen` в шапке (урезан хвост) — явная ошибка `SFW3_NO_ROWMAP`,
а не тихая потеря строк.

Колонки:

- **numeric** — маска null + числовой кодек (`f64 | doubleDelta | gorilla | rle`);
- **dict** — словарь отдельных значений + индекс на строку.

Сжатие блобов: `zstd` (level 3) при Node ≥ 23.8, где он есть в `node:zlib`,
иначе `gzip` (level 6). Явный `compression` в опциях всегда переопределяет дефолт,
но в файл пишется **резолювнутый** способ: если zstd запрошен, а его в Node нет —
файл пишется на gzip (декодировать zstd-файл без zstd — явная ошибка
`SFW3_ZSTD_REQUIRED`). Авто-выбор кодека без явного `codecs` ранжирует **все**
совместимые кодеки на равномерной выборке до 512 значений из столбца (первое и
последнее включены) и победителя прогоняет по всему столбцу один раз — cost
линейно ограничен размером выборки на больших сегментах. Фолбэк при отказе всех
кодеков — `f64`.

```ts
import { Journal } from 'vrack2-journal-db';

const j = new Journal('./data', {
  codecs: { ts: 'doubleDelta', value: 'gorilla' }, // явный кодек; иначе авто-выбор
});
j.open('metrics', { ts: 'delta', value: 'auto' });
j.append({ ts: Date.now(), value: 42.3 });
```

## Числовые кодексы

| Кодек | Когда | Что делает |
|---|---|---|
| `f64` | любой float | 8 байт на значение, базовый |
| `doubleDelta` | таймстампы, счётчики | 2-я разность: у равномерных рядов почти все нули |
| `gorilla` | осциллирующие float (CPU, RAM) | XOR-сжатие соседних значений, без потери точности |
| `rle` | длинные пробеги одного значения | «значение × количество» |
| `simple8b` | маленькие целые (коды, статусы) | 1 байт + run-length |
| `dictionary` | строки | номер в общем словаре |

Кодек выбирается под характер данных: задать явно через `codecs`, или оставить
авто — `autoPickNumCodec` решает по сэмплу (до 512 значений):

1. нет конечных чисел → `f64` (не-числа идут как dict/raw);
2. все целые и средняя длина «пробега» > 3 (до 33 % смен значения) → `rle`;
3. более половины вторых разностей равны нулю (регулярный ряд) → `doubleDelta`;
4. иначе → `gorilla` (осциллирующие float).

На метрических рядах формат даёт ~3× меньше, чем JSON-представление тех же
данных — это проверяется `test/test-v3-format.ts`.

## Структура каталога

```
data/
└── journals/
    └── events/
        ├── seg_1786892460503_0.seg      # закрытый сегмент (бинарный контейнер v4)
        ├── seg_1786892460503_0.seg.meta   # границы ts, счётчики, саммари, dims (~100 байт)
        ├── seg_1786892460503_1.seg
        ├── wal.log                      # `<seq> <json>` строки до flush'а (только при wal: 'on')
        └── .lock                        # блокировка владельца; живёт пока журнал открыт
```

Сегмент — бинарный файл `<имя>.seg` (магические байты `JSDB` + версия 4, затем
по блобу на колонку: числовой кодек или словарь, сжатый zstd/gzip, и CRC32 на
файл).

### Сайдкар `.meta`

Помимо каждого сегмента лежит крошечный сайдкар `<имя>.meta` (или `.seg.meta`) —
JSON из границ и счётчиков (~70 байт). Сам сегмент пишется атомарно (tmp +
rename), а сайдкар — одним `write` сразу за ним: `.meta` — выводимые данные,
при порче или отсутствии `loadClosed()` восстановит их из файла сегмента, так
что лишний `rename` на каждый сегмент не нужен:

- `minTs` / `maxTs` — границы временного диапазона;
- `rowCount` / `physicalRowCount` — логические / реально записанные строки;
- `tsCount` — сколько строк несёт числовой ts (`null` у старых `.meta`);
- `summaries` — саммари числовых колонок (min/max/sum/count) для быстрых агрегаций
  и зональной фильтрации `where` (сегмент целиком пропускается, когда саммари
  доказывают, что ни одна строка не пройдёт условия — только при ts-фильтре,
  т.к. саммари считают только строки с числовым ts);
- `cluster` — поля кластеризации сегмента (`null`, если сегмент не кластеризован);
- `tsOrdered` — `false` у кластеризованных сегментов (порядок внутри — по dims,
  а не по ts); ранний стоп limit-сканов включается только когда `tsOrdered`
  не `false` у всех закрытых сегментов окна;
- `dims` — точные наборы значений (set, до 64) либо числовой диапазон (range)
  по кластеризованным полям — `where` по измерению пропускает сегмент целиком
  даже **без** ts-фильтра; set всегда точен (словарь/пробеги колонки), range —
  консервативная граница для доменов >64 значений;
- `walSeq` — WAL-watermark сегмента: при replay строки WAL с `seq <= max walSeq`
  закрытых сегментов пропускаются (крах между записью сегмента и усечением WAL
  не даёт дублей);
- `bytes` — размер файла сегмента в байтах: статистике не нужен `stat` по каждому
  файлу.

Благодаря ему `stats()`, `getTimeRange()`, `Store.describe()` и пропуск файлов в
`query()` и `aggregate()` работают **без единого разжатого файла**. Все поля
`.meta` — выводимые: при отсутствии или порче сайдкара `loadClosed()`
восстанавливает их из сегмента (детерминированно, включая `dims`).

### Содержимое сегмента (JSON-представление)

Логическая структура сегмента (в файле числовые колонки — в кодеках, а rowMap —
бинарный хвост u32):

```json
{
  "id": "seg_1786892460503_0",
  "schema": { "ts": "delta", "level": "dictionary" },
  "metadata": { "owner": "me" },
  "rowCount": 100,
  "physicalRowCount": 85,
  "minTs": 1700000000,
  "maxTs": 1700000099,
  "tsCount": 100,
  "walSeq": 100,
  "columns": {
    "ts":     { "type": "delta", "baseValue": 1700000000, "deltas": [1, 1, ...] },
    "level":  { "type": "dictionary", "dictionary": ["info", "warn", "error"], "data": [0, 1, 2, ...] }
  },
  "summaries": { "value": { "min": 0, "max": 99, "sum": 4950, "count": 100 } },
  "rowMap": [0, 0, 0, 1, 2, ...]
}
```

`rowCount` — сколько строк «видит» читатель; `physicalRowCount` — сколько реально
записано (разница — дедупликация, см. `Maintenance.md`); `rowMap[i]` — к какой
физической строке относится i-я логическая (в файле — бинарный хвост u32);
`walSeq` — WAL-watermark (см. сайдкар `.meta`).

Метаданные в сегменте — снимок на момент его записи: позднее `updateMetadata()`
влияет только на журнал и будущие сегменты, уже записанные файлы не переписываются
(сегменты неизменяемы).

# Архитектурный план: журнал → метрический движок

Цель — превратить vrack2-journal-db из append-only журнала событий во
встраиваемый метрический движок по мотивам двух идей:

- **ClickHouse (упрощённый)**: колонные кодексы, векторизованные агрегации,
  min/max-приннинг сегментов — без SQL-диалекта, репликации и мутаций;
- **GraphiteMergeTree**: retention-тиры вида `'5s:1d,15s:1w,1m:1mon'` —
  свежие данные с высокой плотностью, старые — агрегированные, размер на
  диске предсказуем.

При этом сохраняем главное достоинство базы: **без сервера и зависимостей,
каталог = база**, можно копировать, бэкапить `tar`'ом, читать файлы напрямую.

## 0. Цели и не-цели

**Цели**

- `avg/min/max/sum/count` и `downsample` по диапазону без материализации строк;
- бинарные кодексы колонок (doubleDelta, XOR/Gorilla, RLE) — плотное
  хранение числовых рядов;
- retention-тиры: одна «таблица» = N журналов с разным разрешением;
- каждый этап самостоятельно releasable и не ломает старые данные.

**Не-цели** (осознанно)

- SQL, произвольные индексы, транзакции, репликация, distributed;
- обновление/удаление отдельных строк (append-only остаётся);
- гарантированная точность при rollup — агрегация теряет детали бакета,
  это семантика Graphite/Whisper, фиксируем в README.

## 1. Что уже есть (фундамент)

| Механизм | Статус |
|---|---|
| Journal / Segment / Column, 6 стратегий (raw, dictionary, delta, rle, auto, catchall) | есть |
| WAL + атомарные сегменты (tmp+rename) + PID-лок | есть |
| `.meta`-сайдкар (minTs/maxTs, rowCount, tsCount) — чтение без разжатия файлов | есть |
| `compact()` (дедупликация на границах, перекодирование auto) | есть |
| `purge(beforeTs)` по `.meta`, `timeline(interval, period)` | есть |
| интервальный язык (VRackDB): `'now-1h'`, `'1m'`, `roundTime()` | есть |
| форматы v1 (JSON) / v2 (gzip+JSON+CRC32), мульти-версионный reader | есть |
| LRU-кэш сегментов, Store с общим кэшем | есть |

Чего нет: агрегации, даунсэмплинг, модель «таблица/серии», бинарные кодексы,
векторный скан.

## 2. Целевая архитектура

```
Table (имя + retention-тиры + политика rollup)
 ├── Journal r5s   — разрешение 5с,  TTL 1d
 ├── Journal r15s  — разрешение 15с, TTL 1w
 └── Journal r1m   — разрешение 1m,  TTL 1mon
      └── Segment (immutable, бинарный v3)
           └── Column = цепочка кодеков + саммари (min/max/sum/count)

Писатель:  Table.append → самый мелкий тир (WAL → сегмент)
Читатель:  Table.query(range) → разбиение на age-окна → Journal.aggregate() → векторный скан
Обслуживание: rollup (mелкий→крупный, по сегментам) + purge (TTL тира)
```

Ключевой принцип: **всё строится по сегментам, а не по строкам**. Сегмент
неизменяем → саммари считаются один раз, rollup идемпотентен, pruning — по
метаданным без чтения данных.

## 3. Фазы

### Фаза 1. Сегментные саммари + агрегации (без смены формата)

Самое высокое отношение «польза/стоимость»: снимает главное ограничение
«2M строк в память за 1.5 c».

1. **Саммари числовых колонок**: при закрытии сегмента считать
   `min/max/sum/count` каждой числовой колонки (null не считаются) и писать
   в `.meta` + в заголовок сегмента (чтобы старые `.meta` не были критичны).
2. **`Journal.aggregate(startTs, endTs, exprs)`**:
   ```ts
   j.aggregate('now-1h', 'now', [
     { field: 'value', fn: 'avg' },
     { field: 'value', fn: 'min' },
     { field: 'value', fn: 'max' },
     { field: 'value', fn: 'count' },
   ]);
   // → { avg: 42.3, min: 1.0, max: 99.9, count: 7184 }
   ```
   Сегмент целиком в диапазоне → берётся из саммари (sum/count для avg);
   граничные сегменты → скан одной колонки (не всех).
3. **`Journal.downsample(startTs, endTs, bucketMs, field, fns)`** — расширение
   `timeline()`: бакеты + агрегаты в каждом (использует `roundTime()`).
4. Семантика null: `count` — только непустые; `sum/avg/min/max` — пропускают
   null. Строки без `ts` — вне агрегаций (как сейчас).

**Тесты**: `test-aggregate.ts` — сверка с brute-force (`allRows()` + ручный
расчёт) на случайных данных, включая null, границы бакетов, сегменты без `.meta`.
**Приёмка**: агрегат по 2M строк без создания массива строк (контроль RSS);
`avg` по диапазону ≥ 10x быстрее `allRows()` + reduce.

### Фаза 2. Кодек-фреймворк и бинарный формат v3

«Путь движков»: данные на диске перестают быть JSON'ом.

1. **Интерфейс кодека**:
   ```ts
   interface NumCodec {
     encode(values: ArrayLike<number>): Buffer;
     decode(buf: Buffer, n: number): Float64Array | Int32Array;
   }
   ```
   Цепочка на колонку: `значение → числовой кодек → сжатие (zstd|gzip) → CRC32`.
2. **Числовые кодексы**:
   - `doubleDelta` — вторые разности (timestamp'ы, счётчики; у равномерных
     рядов почти все нули);
   - `gorilla`/XOR — осциллирующие float (CPU, RAM): XOR соседних double
     медленно меняющихся значений даёт длинные нулевые биты; хранение без
     потери точности (полный double восстанавливается);
   - `rle8`/simple8b — маленькие целые (коды, счётчики);
   - `dictionary` — строки (уже есть, переиспользуем).
3. **Формат v3**: `JSDBv3` + заголовок (JSON: схема, кодек каждой колонки,
   rowCount, саммари) + бинарные блобы колонок + таблица смещений + CRC32.
   Reader мульти-версионный: v1/v2 читаются как сейчас; запись — только v3.
4. **Выбор кодека**: явно в схеме (`val: { type: 'numeric', codec: 'gorilla' }`)
   или авто (расширение существующей эвристики auto на 50 сэмплах).
5. Сжатие: gzip по умолчанию (Node ≥ 18), zstd — опция (Node ≥ 23.8),
   переключается на уровне цепочки, формат не меняется.

**Тесты**: `test-codecs.ts` — fuzz roundtrip encode/decode (включая NaN-защиту,
пустые колонки, 1 значение), сравнение байт/точку с v2 на метрических данных.
**Приёмка**: метрика «ts + value(float)» ≤ ~8–12 байт/точку на диске;
100% roundtrip; старые v1/v2-каталоги читаются без миграции.

### Фаза 3. Векторный скан и запросы

1. **`Journal.scan(opts)`**:
   ```ts
   j.scan({
     start: 'now-1h', end: 'now',
     select:  ['ts', 'value', 'host'],
     where:   [{ field: 'value', op: 'gt', value: 90 }],
     groupBy: 'host',
     agg:     { value: ['avg', 'min', 'max'], ts: ['count'] },
     order:   'desc', limit: 20,
   });
   // → [{ host: 'web-1', value_avg: 73.2, ..., count: 1420 }, ...]
   ```
2. Механика: декодировать **только выбранные колонки** в TypedArray; фильтр —
   плотный цикл с ранним выходом; агрегаты — накопители; `groupBy` — hashmap
   по декодированной колонке с частичными агрегатами на сегмент и merge.
3. Память: O(выбранное число колонок × размер сегмента) на время скана +
   O(#групп), а не O(#строк × #полей) как в `allRows()`.
4. `allRows()/query()/tail()/page()` остаются как есть (совместимость);
   внутренне могут переиспользовать тот же сканер.

**Тесты**: `test-scan.ts` — сверка с brute-force по where/groupBy/order/limit,
композиции условий, пустые выборки, high-cardinality groupBy (limit top-k).
**Приёмка**: 10M точек, 2 колонки, where + group by 50 групп + avg/min/max —
< 1–2 с и < 150 МБ RSS на Apple Silicon.

### Фаза 4. Table + retention-тиры (GraphiteMergeTree)

1. **API**:
   ```ts
   const t = store.openTable('cpu', {
     retention: '5s:1d,15s:1w,1m:1mon',   // resolution:duration, парсер уже есть
     agg:     { value: 'avg' },           // что держать в бакете
     schema:  { ts: 'delta', value: { type: 'numeric', codec: 'gorilla' }, host: 'dictionary' },
   });
   t.append({ ts: Date.now(), host: 'web-1', value: 42.3 });
   t.query('now-30d', 'now');   // сам собирает ответ из нужных тиров
   t.stats();                   // { tiers: [{ r: '5s', rows: …, size: … }, …] }
   ```
2. **На диске**: `data/journals/cpu/r5s| r15s|r1m/…` — обычный журнал на тир;
   TTL тира = его duration (авто-`purge()` при open/close/интервале).
3. **Rollup** (аналог merge): по сегментам, не по строкам:
   - сегмент мелкого тира с `maxTs < now - TTL_мелкого` → `downsample()`
     (фаза 1) по бакетам разрешения следующего тира → дописать в крупный тир;
   - сегмент удалён (purge-механика);
   - **чекпоинт** (последний rolled `maxTs` на тир) пишется атомарно
     ДО удаления сегментов → краш посреди rollup = повторный rollup того же
     окна идемпотентно (сегменты неизменяемы, границы бакетов детерминированы
     через `roundTime()`);
   - запуск: явный `t.rollup()`, `t.rollupInterval('10m')` или на `open()`.
4. **Чтение**: диапазон разбивается по «возрасту» на окна тиров
   (`now-1d:now` → r5s, `now-1w:now-1d` → r15s, `now-1mon:now-1w` → r1m);
   внутри тира — pruning по `.meta`; ответ склеивается в хронологическом порядке.
5. **Валидация конфига**: разрешения кратны предыдущим (5s|15s|1m ✓),
   durations неубывающие (1d < 1w < 1mon ✓) — иначе явная ошибка с подсказкой.

**Тесты**: `test-table.ts` — жизненный цикл тира, идемпотентность rollup
(краш в середине через crash-writer из test/helpers), query через границы тиров,
валидация конфига, `stats()` по тирам.
**Приёмка**: 30 дней метрик 5s — итоговый размер ≤ Σ(TTL_tir × разрешение_tir);
запрос «последний час» читает только r5s, «прошлый месяц» — только r1m.

### Фаза 5. Опциональные расширения (после M3)

- SQL-lite поверх `scan()` (SELECT … WHERE t BETWEEN … GROUP BY …) — тонкий
  парсер, не диалект;
- top-k групп, `quantile` (t-digest по сегментам);
- zstd по умолчанию при Node ≥ 23.8;
- lazy-миграция v1/v2 → v3 при `compact()` / отдельная команда.

## 4. Ключевые решения

| # | Решение | Почему |
|---|---|---|
| 1 | Тир = отдельный журнал (а не поле «разрешение» в строке, как в CH) | Совпадает с append-only и лок-моделью; на диске — просто подкаталоги |
| 2 | Rollup — явная задача (tick/interval/ручной), а не «при merge» | Управляемо, тестируемо, не мешает записи; CH делает то же фоновым merge'ом |
| 3 | v3 — добавочный формат, v1/v2 читаются | Backward-совместимость — уже устоявшаяся модель (v1→v2) |
| 4 | Агрегации — отдельный API (`aggregate/scan`), не SQL | Ядро остаётся простым; SQL-обёртка — фаза 5, если понадобится |
| 5 | Rollup lossy по дизайну | Семантика Graphite/Whisper; фиксировать в README + `agg` в конфиге тира |
| 6 | Один писатель на журнал (текущий PID-лок) | Table-фасад — единственный владелец всех тиров; fan-in вне модели |

## 5. Риски и меры

| Риск | Мера |
|---|---|
| Потеря точности float в XOR-кодеке | Кодек без потерь (хранение XOR + базовый double); fuzz roundtrip |
| GroupBy высокой кардинальности → память | `limit`/top-k в API; частичные агрегаты на сегмент |
| zstd недоступен на Node 18 | gzip по умолчанию, zstd — опция цепочки |
| Краш посреди rollup | Чекпоинт до удаления сегментов + идемпотентное повторение |
| Дубли при rollup (окно уже дописано) | Чекпоинт по `maxTs` + проверка `minTs` целевого тира |
| Случайный nonce в id сегментов ломает порядок | Устранено (сортировка по (tsMs, counter) + дет. регресс-тест, см. 55531d5) |

## 6. Тестирование и бенчмарки

- Каждый этап — отдельный файл сценария в `test/` (существующий стиль:
  `N passed / M failed`, brute-force сверки).
- `test-load.ts` расширить метрическим workload'ом (осциллирующий value):
  сравнить v2 и v3 — байт/точку, скорость записи, время `aggregate()` на 2M–10M точек.
- Детерминизм: всё, что зависит от случайностей (nonce, время), — фиксировать
  переименованием файлов/заглушками, как в регресс-тесте порядка сегментов.

## 7. Магазинные вехи

| Веха | Содержимое | npm |
|---|---|---|
| **M1** | Фаза 1: саммари + `aggregate()` + `downsample()` | 1.3.0 |
| **M2** | Фазы 2–3: кодек v3 + векторный `scan()` | 1.4.0 |
| **M3** | Фаза 4: `Table` + retention-тиры + rollup | 2.0.0 |

Каждая веха — самодостаточный релиз: M1 уже даёт «среднее за час» без
материализации, M2 — плотное хранение и быстрые срезы, M3 — предсказуемый
размер на 30+ дней метрик.

# Надёжность и целостность

Краш в момент записи не должен терять данные или ломать файл; два процесса не
должны писать в один журнал одновременно. Здесь — как это устроено: WAL, атомарная
запись сегментов, восстановление после краха, блокировка, проверка целостности.

## WAL — журнал предзаписи

Строки не пишутся в файл сегмента по одной. Сценарий:

1. **Строка сначала уходит в WAL** — файл `wal.log` (write-ahead log). Одна строка
   — одна JSON-строка в файле. Запись на диск идёт пачками (по умолчанию 512 строк
   или 1 МБ накоплено — один системный вызов вместо одного на строку), но буфер
   гарантированно сбрасывается при любом выходе процесса: `close()`,
   `process.exit()`, SIGINT/SIGTERM, uncaught exception. Значит: даже если процесс
   мгновенно умрёт после `append()` — строки уже на диске и не потеряны
   (исключение — только `kill -9`/сбой питания; это ограничение любой WAL).

2. **Сегмент записывается атомарно.** Когда сегмент заполняется, он сначала
   пишется во временный файл `<имя>.json.tmp` (или `.seg.tmp` для v3), и только когда
   запись полностью завершена — переименовывается в `<имя>.json`/`<имя>.seg`.
   Переименование на одной файловой системе атомарно: наблюдатель видит либо старый
   мир (файла ещё нет), либо новый (файл целиком). Полувыверенного файла не бывает.
   Сразу после этого `wal.log` удаляется — все его строки уже внутри сегмента.

3. **При следующем открытии** журнал проверяет: есть ли в каталоге `wal.log`?
   Если да — значит, предыдущий процесс умер до flush'а. Строки из него
   проигрываются в активный сегмент (в том числе с дедупликацией), файл удаляется.
   Дальше журнал работает как ни в чём не бывало: `allRows()` вернёт и старые,
   и «спасённые» строки.

## Блокировка владельца

По умолчанию (`lock: 'pid'`) при открытии журнал создаёт файл `.lock` со своим
PID — это маркер «журнал занят». Второй процесс, пытающийся открыть тот же журнал,
получает ошибку вида `Журнал заблокирован процессом 12345`. Если владелец блокировки
умер (процесса с таким PID больше нет), новый процесс забирает блокировку себе —
ручную «разблокировку» делать не нужно. При `close()` блокировка снимается.

Опция `lock: 'off'` отключает и создание, и проверку `.lock`: библиотека больше
не участвует в координации владельцев, это становится ответственностью приложения.

```ts
const j = new Journal('./data', { lock: 'off' }); // или Store({ lock: 'off' })
// override для одного журнала: store.openJournal('x', schema, {}, { lock: 'pid' | 'off' })
```

Когда это нужно: типичный случай — база внутри **worker_threads**. Воркер
разделяет PID с основным процессом, поэтому если воркер умирает (краш,
`terminate()`), его `.lock` выглядит как блокировка живого процесса и журнал
«застревает» до перезапуска приложения. Если вы сами контролируете владельца
(один воркер-обработчик + IPC, свой supervisor), открывайте с `lock: 'off'` —
и не забудьте снять осиротевший `.lock`, если база уже «застряла»:

```ts
fs.rmSync(path.join(dataDir, 'journals', <имя>, '.lock'), { force: true });
```

Семантика при нескольких открытых инстансах одного журнала: каждый видит данные на
момент своего `open()` плюс то, что записал сам; новые сегменты другого инстанса
становятся видны после `close()`/reopen. Данные на диске сходятся в любом случае —
просто «живой» обмен между открытыми инстансами не предусмотрен.

## Целостность файлов

Новые файлы сегментов имеют магические байты `JSDB`, версию формата, полезную
нагрузку (gzip-сжатый JSON в v2, числовые кодексы в v3) и 4-байтовую контрольную
сумму (CRC32) в конце. При чтении сумма проверяется **до** разжатия — повреждённый
файл (обрыв записи, битые сектора) отклоняется с явной ошибкой «повреждён:
контрольная сумма не совпала», а не превращается в мусорные данные.

Старые файлы v1 (чистый JSON, как у JS-версии из `../new`) читаются без изменений —
база backward-совместима. Подробнее о байтовом layout — в `Formats.md`.
